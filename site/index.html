Noisefloor

Flaky tests and runtime regressions in CrashCart's Jenkins build history, found by a data pipeline (Jenkins → DuckDB → dbt).

Summary

Flaky tests

A test is flaky when it both passed and failed on the same commit: the code didn't change, the result did. The flip rate is the share of back-to-back runs whose result switched between pass and fail, over the last 30 days.

30-day flip rate over time

Each point is the flip rate over the 30 days ending that day. Days with fewer than 10 pairs of runs in the window aren't plotted; the table lists them.

Runtime regressions

A passed run is a regression when it takes more than 1.5× the median of the test's previous 20 passed runs and at least 0.5 s longer. Three or more such runs in a row are a sustained regression; fewer are a spike, usually timing noise.

About this data

  • Source: a local Jenkins in Docker building CrashCart's noisefloor-demo branch: its unit, API and demo tests per build, with no retries.
  • Demo tests are synthetic. They're flaky or slow by design, and seeded from the build number so results can be rebuilt exactly. The unit and API tests are real.
  • Simulated time. Every build ran on one day. To show the 30-day window working, the newest build keeps its real time and each earlier build is placed 18 hours before the next. Real times are kept in the data alongside.
  • Every number on this page is generated by the pipeline. Source: github.com/kartikey3112/noise-floor.
